# 第一阶段：产品与架构设计

> 本文档是 LabAgent 从参考项目 JavaLabAgent（Spring Boot + Spring AI）迁移和升级到 Python（FastAPI + LangChain/LangGraph）技术栈的第一阶段产出。
> 目标：明确产品定位、核心用户故事、V2 功能边界、技术架构、API 兼容清单，以及数据库复用与迁移方案。
> 文档严格区分「本阶段迁移目标」与「未来规划」，架构描述均为设计方案，尚未落地实现。

---

## 一、一页产品说明

**LabAgent** 是一个面向教学实验的 Agentic RAG 平台。

学生在使用校内实验教学 / 作业平台时，经常遇到重复性问题（实验要求不清、报告格式、OJ 平台使用、代码报错排查等），频繁咨询老师，教师答疑成本高。LabAgent 通过「Agentic RAG + 三级检索 + RAGAS 评测闭环 + 多模型接入 + 沙箱隔离与工具安全控制」为学生提供可信、可溯源、可持续优化的自助答疑能力。

核心价值：

- **减少重复咨询成本**：把高频问题沉淀进课程私有知识库，通过 Agentic RAG 自动检索和组织回答。
- **提高回答可信度**：结合三级检索、重排和来源引用，优先基于知识库与工具结果回答，减少模型幻觉。
- **形成评测优化闭环**：通过 RAGAS 等评测指标持续观察召回质量、回答相关性和忠实度。
- **私有化部署**：支持本地大模型（Ollama）与私有向量库（PostgreSQL + pgvector），可离线运行，保护教学数据。
- **教学场景贴合**：围绕实验要求、报告规范、平台操作、代码报错排查等真实需求设计工具与知识结构，并通过沙箱隔离控制工具风险。

目标用户：

- **学生**：自助获取实验要求、报告规范、平台操作指引、代码报错解释。
- **教师 / 管理员**：维护课程知识库、管理用户与账号、查看并处理用户反馈。

技术定位（V2）：以 **Python + FastAPI + LangChain/LangGraph** 重写 JavaLabAgent，保留 RAG 闭环、会话记忆、Skills、流式输出等已验证能力，采用「有限状态图 + 受控工具」的 Agent 形态，而非完全自由的 Agent。

## 二、核心用户故事

### 学生

- 作为学生，我希望**注册 / 登录**系统，以便使用我的独立会话和历史记录。
- 作为学生，我希望**新建会话并连续多轮提问**，以便围绕一个问题深入交流。
- 作为学生，我希望**查看、切换、删除我的历史会话**，以便管理过往交流。
- 作为学生，我希望提问后**实时看到流式回答**，以便更快获得反馈。
- 作为学生，我希望回答能**标注来源**（知识库 / 通用知识）并给出引用文档，以便判断答案可信度。
- 作为学生，我希望询问「实验几的提交时间和报告要求」时，系统能**基于课程知识库准确回答**。
- 作为学生，我希望粘贴 Java 报错信息时，系统能**解释异常原因并给出排查建议**。
- 作为学生，我希望询问「如何在实验平台提交代码」时，系统能**给出平台操作步骤**。
- 作为学生，我希望能**提交反馈**（BUG / 建议 / 投诉），以便反映使用问题。

### 教师 / 管理员

- 作为管理员，我希望**上传课程文档**（PDF / Markdown / TXT）到知识库，系统能自动解析、切分、向量化。
- 作为管理员，我希望上传 **QA 文档**时按「问—答」对整体切分，保证语义完整。
- 作为管理员，我希望**查询、下载、删除**知识库文件，且删除时**同步清理向量数据**，保证一致性。
- 作为管理员，我希望**新增用户、分页查询用户、启用 / 禁用账号**，以便管理系统成员。
- 作为管理员，我希望**管理接口有权限校验**，非管理员无法访问。

### 安全相关（贯穿所有故事）

- 作为系统，我必须从 **JWT 身份**中获取当前用户 ID，绝不信任请求体传入的 `userId`。
- 作为系统，我必须对**上传文件**校验大小、类型、扩展名与文件名。
- 作为系统，我必须使用 **Argon2 / bcrypt** 存储密码（替换参考项目的 MD5）。

### 4.2 Agent 有限状态图（V2 目标形态，第四阶段落地）

```
识别问题 → 检索课程知识 → 判断是否需要工具 → 执行工具 → 生成答案 → 安全检查 → 保存结果
```

第一批受控工具建议（第四阶段实现）：`search_course_knowledge`、`get_experiment_requirements`、`get_platform_guide`、`analyze_java_error`、`get_report_requirements`。

### 4.3 RAG 链路

```
文档解析 → 切分(QA/Token) → 向量化(1024维) → 检索(TOP_K + 相似度阈值) → 过滤 → 提示词拼接 → 生成 → 来源标注
```

关键参数（沿用参考项目，可通过 Settings 配置）：

- 向量维度：`1024`（需与嵌入模型输出一致）
- 索引：pgvector `HNSW` + 余弦距离
- 检索：`TOP_K = 10`，`SIMILARITY_THRESHOLD = 0.71`

## 六、数据库复用与迁移方案

### 6.1 复用策略

V2 继续使用 **PostgreSQL + pgvector**，表结构得具体看看如何设计，通过 **SQLAlchemy 2.0 + Alembic** 管理模型与迁移。核心表可直接复用，仅在字段语义与安全上做必要调整。

### 6.2 表清单与迁移动作

| 表 | 用途 | 迁移动作 |
| :--- | :--- | :--- |
| `vector_store` | RAG 向量存储（1024 维 + HNSW 余弦索引） | 直接复用；由 LangChain PGVector 对接 |
| `tb_user` | 用户信息 | 复用；`password` 存储改为 Argon2/bcrypt；建议 `id` 改为自增/序列，`create_time`/`update_time` 用 timestamp |
| `chat_session` | 会话 | 直接复用（含 `summary`、逻辑删除 `deleted`） |
| `chat_message` | 消息（预留 `embedding`） | 直接复用 |
| `ali_oss_file` | 文件记录（文件名 / URL / vector_id） | 复用；建议重命名为 `kb_file` 以脱离「阿里云」语义，字段保持兼容 |
| `tb_user_feedback` | 用户反馈 | 直接复用 |

扩展依赖：`vector`、`hstore`、`uuid-ossp`（沿用 init.sql 中的 `CREATE EXTENSION`）。

### 6.3 需要处理的兼容性问题

1. **密码哈希**：参考项目用 MD5（`0192023a...` 为 MD5(admin)），V2 必须改为 Argon2/bcrypt。初始管理员账号需重新生成哈希写入迁移脚本。
2. **用户 ID 类型**：`tb_user.id` 当前为手工整数主键，V2 建议用序列 / 自增，避免注册时手工分配 ID。
3. **文件表命名**：`ali_oss_file` 语义绑定阿里云，V2 仅用 MinIO，建议逻辑上视为通用文件表（物理名可保留以兼容存量数据）。
4. **`vector_id` 一致性**：删除文件时须同步删除 `vector_store` 中对应片段，保证「文件—向量」一致性。
5. **Alembic 基线**：以现有 `init.sql` 为初始迁移基线，后续变更全部通过 Alembic 版本管理。

### 6.4 迁移执行方式

- 全新部署：Alembic `upgrade head` 建表 + 初始化管理员（Argon2 哈希）+ pgvector 扩展。
- 复用存量数据：保留 `chat_session` / `chat_message` / `vector_store` / `tb_user_feedback` 数据；`tb_user.password` 需一次性重置或引导用户改密。

## 七、三类核心演示问题

用于第一阶段验收与后续 RAG 评测的锚点问题，分别覆盖「知识库检索」「代码报错排查」「平台操作指引」三类场景：

1. **实验要求 / 报告规范（知识库检索）**
   「实验三什么时候提交，报告有什么要求？」
   —— 期望：命中课程知识库，标注 `【根据知识库】：`，给出提交时间与报告要求，并附引用来源。

2. **代码报错排查（工具 + 知识库）**
   「为什么我的 Java 程序出现空指针异常？」
   —— 期望：解释 NPE 成因，给出常见触发场景与排查步骤（未来由 `analyze_java_error` 工具增强）。

3. **平台操作指引（知识库检索）**
   「我不会使用实验平台提交代码，应该怎么操作？」
   —— 期望：命中平台使用说明知识，给出分步操作指引（未来由 `get_platform_guide` 工具增强）。

## 八、本阶段结论

- 产品定位、用户故事、功能边界已明确；V2 采用「有限状态图 + 受控工具」的稳健 Agent 形态。
- API 与数据库以「最大化兼容参考项目、最小化前端改动」为原则，安全项（JWT 取用户、管理员校验、密码哈希、文件校验）从第一天纳入设计。
- 本文档为设计方案，尚未落地；具体实现见后续阶段（第二阶段：基础后端 → 第三阶段：RAG 闭环 → 第四阶段：LangGraph Agent）。
