# Ollama 双实例负载均衡设计

## 1. 目标与结论

当前部署：

| Endpoint | GPU | 主模型 |
| --- | --- | --- |
| `http://172.29.7.233:11434` | GPU 0 | `qwen3.5:35b` |
| `http://172.29.7.233:11435` | GPU 1 | `qwen3.5:35b` |

设计结论：

1. 默认聊天模型切换为 `qwen3.5:35b`。
2. 后端对每次 Ollama 模型调用执行“最少进行中请求优先，相同时轮询”，在两个 Endpoint 之间分发。
3. 一次流式模型调用选定 Endpoint 后保持不变，禁止在生成过程中切换实例。
4. 跨 Endpoint 失败重试默认关闭，避免两个实例同时异常时累计等待；按需开启后，仅允许在首个 Token 返回前换实例重试一次。
5. 聊天、标题生成、查询改写、LLM rerank 和 Embedding 全部接入双实例；上线前确认两个实例的模型名称、版本和向量维度一致。

当前方案已完成第一版实现。

## 2. 当前实现与切换范围

`ModelProvider` 已统一管理双实例 Endpoint 池，聊天与 Embedding 模型通过负载均衡代理执行真实调用。前后端默认模型已同步为 `qwen3.5:35b`。

已实施范围：

| 位置 | 调整 |
| --- | --- |
| 后端默认配置 | `ollama_chat_model` 默认值为 `qwen3.5:35b` |
| 部署环境 | `OLLAMA_CHAT_MODEL=qwen3.5:35b` |
| 前端模型列表 | 默认值及展示名称为 `qwen3.5:35b` / `Qwen3.5-35B` |
| 双实例配置 | 使用 `OLLAMA_BASE_URLS`，未配置时回退 `OLLAMA_BASE_URL` |

第一版只新增必要配置：

```dotenv
OLLAMA_BASE_URLS=http://172.29.7.233:11434,http://172.29.7.233:11435
OLLAMA_BASE_URL=http://172.29.7.233:11434
OLLAMA_RETRY_OTHER_ENDPOINT_ON_FAILURE=false
OLLAMA_CHAT_MODEL=qwen3.5:35b
```

配置中的 Endpoint 只能来自服务端环境变量，不能接受前端传入，避免 SSRF。

## 3. 方案设计

### 3.1 组件职责

在 `ModelProvider` 内增加轻量的 `OllamaEndpointPool`，不改变 LangGraph 编排：

- 保存 Endpoint 的进行中请求数和轮询游标。
- 选择进行中请求最少的 Endpoint，数量相同时使用轮询打破平局。
- 将选中的 `base_url` 传给 `ChatOllama`，继续使用 LangChain 统一 `Runnable` 接口。
- 模型调用完成后释放进行中请求计数，并记录成功或失败。

LangChain 的 `ChatOllama` 原生支持在构造时指定 `base_url`，因此负载均衡只负责选择地址，不自行实现模型客户端或 Agent 循环。

### 3.2 分发流程

```text
模型调用
  -> 获取可选 Endpoint
  -> 选择 in_flight 最少的节点
  -> 数量相同则按 11434 / 11435 轮询
  -> 创建绑定该 Endpoint 的 ChatOllama
  -> 执行完整 invoke/astream
  -> 更新进行中请求数
```

负载均衡粒度是“一次模型调用”，不是一次 HTTP 会话。一个 Agent 请求可能多次调用模型，每次均可重新选择 Endpoint；单次 `astream` 内必须固定 Endpoint。

精确选择规则：

1. 排除本次重试中已经失败的 Endpoint。
2. 比较其余节点的本进程 `in_flight` 数量，选择最小者。
3. 两个节点数量相同，按 `11434 -> 11435 -> 11434` 轮询。
4. 选中后立即将该节点 `in_flight + 1`，调用结束或取消后减一。
5. 两个节点在本次调用中都失败时，由现有 SSE 错误流程返回明确提示。

不根据 GPU 利用率分发：Ollama 没有提供适合逐请求调度的标准 GPU 负载接口，额外采集 `nvidia-smi` 会增加部署耦合，而且采样值很快过期。

不根据问题难度分发：两个 Endpoint 的模型和算力相同，难度分类本身还需要额外推理，会增加延迟且不能可靠预测实际生成时间。

`in_flight` 只用于选择，不在后端强制设置并发上限；实际并行度和排队交给 Ollama，避免 `MAX_IN_FLIGHT=1` 让后端额外阻塞。后续根据压测结果再决定是否限流。

### 3.3 失败处理

正常请求只做一次内存选择，不执行额外健康检查，耗时可以忽略。

- 默认情况下，模型调用出现连接失败、连接超时或服务端故障时直接失败，不再改投另一节点。
- `OLLAMA_RETRY_OTHER_ENDPOINT_ON_FAILURE=true` 时，才允许在安全边界内改投另一节点一次。
- 不维护跨请求故障冷却；下一次新调用仍可正常选择两个 Endpoint。
- 每次失败只记录一条精简日志：调用类型、Endpoint、模型、异常类型与信息、是否已输出 Token、耗时。
- 模型正常返回的业务错误不视为节点故障。

`GET /api/ps` 可用于观测模型是否已加载及显存占用，但不作为唯一健康依据，避免模型尚未预热时被误判为不可用。

### 3.4 重试边界

| 场景 | 处理 |
| --- | --- |
| 建连失败、首 Token 前超时或 5xx | 默认直接失败；开关开启后排除当前节点并换另一节点重试一次 |
| 已向前端输出 Token | 不透明重试，返回中断错误，避免拼接两份答案 |
| 模型不存在 | 摘除该节点并报警，不在同一节点反复请求 |
| 两个节点都不可用 | 快速失败，不回退到未配置的外部模型 |
| 客户端主动取消 | 取消当前调用并释放计数，不触发重试 |

工具调用可能产生副作用，但这里重试的是“模型推理请求”，不是 Tool 执行；现有 ToolNode 不应因模型重试而重复执行已完成的工具。

## 4. Embedding 与模型装载

两个实例都已部署 Embedding 模型，因此查询向量化和知识库批量向量化也使用相同的 Endpoint 选择器。

需要重点验证 `qwen3.5:35b` 与 Embedding 模型能否同时驻留单卡显存。如果显存不足，聊天与 Embedding 交替调用会触发模型装载或卸载，这比负载均衡选择本身慢得多。上线前通过 `/api/ps` 和实际压测确认：

- 两个模型可同时驻留：聊天和 Embedding 都在双实例间分发。
- 频繁发生模型换入换出：知识库批量 Embedding 固定到低峰期，或为 Embedding 单独保留实例/资源，不能依赖轮询解决。

## 5. 多进程说明

内存中的轮询游标和计数仅在单个后端进程内准确。当前单进程部署可直接采用；若未来启用多个 Uvicorn Worker 或多个后端副本，各进程会独立轮询，整体仍能分流但不是严格全局均衡。届时优先将均衡下沉到独立反向代理，或使用 Redis 维护全局租约，不在第一版提前增加复杂度。

`kb-worker` 与 Web 后端也是独立进程，双方的 `in_flight` 不能互相感知。第一版接受这种近似分流；若批量 Embedding 明显影响在线聊天，应优先限制 Worker 并发或错峰处理。

## 6. 可观测性与安全

日志和指标只记录 Endpoint 标识、模型、耗时、首 Token 延迟、结果状态和重试次数，不记录 Prompt、JWT 或完整模型输出。

建议指标：

- 每个 Endpoint 的请求数、成功率、进行中请求数。
- 首 Token 延迟与总耗时。
- 健康探测结果、摘除与恢复次数。
- 重试次数和“双节点不可用”次数。

两个 Ollama 端口应仅允许后端所在网络访问；若跨主机网络不可信，应增加反向代理鉴权或 TLS，不能把鉴权信息写入日志。

## 7. 实施状态与验收

已完成：

1. 同步默认模型、前端模型列表和部署环境配置。
2. 实现 Endpoint 配置解析、最少进行中请求选择及轮询打破平局。
3. 接入聊天、标题、查询改写、rerank 和 Embedding。
4. 增加选择、精简失败日志、默认不重试、可选首 Token 前重试和流式中断测试。

部署验收：

1. 在两个实例执行 `/api/tags`，确认聊天与 Embedding 模型名称、版本和向量维度一致，并分别完成预热。
2. 小流量观察两块 GPU 的请求数、显存、模型换入换出和延迟。

验收标准：

1. 连续请求在两个健康 Endpoint 之间近似均匀分布。
2. 正常请求持续在两个实例间轮询；单节点失败时默认直接返回，开启失败重试后才自动改投另一实例。
3. 流式回答不会在实例间切换，也不会因重试产生重复内容。
4. 两个实例都不可用时，在受控超时内返回明确错误。
5. 页面默认选择和后端兜底模型均为 `qwen3.5:35b`。
6. 现有 LangGraph、Tool Calling、RAG 引用和 SSE 协议保持不变。
7. Embedding 向量维度保持不变，不影响现有 pgvector 数据。
