# 部署与模型接入

## 1. Docker Compose

当前 `docker-compose.yml` 编排：

| 服务 | 作用 |
|---|---|
| `postgres` | 业务数据、LangGraph checkpoint 和 pgvector |
| `redis` | ARQ 队列与接口缓存（使用不同逻辑 DB） |
| `minio` | 原始知识文档 |
| `backend` | FastAPI |
| `kb-worker` | 文档解析、切分和索引 |
| `tool-runner` | 受控 Shell 执行 |
| `frontend` | Web 前端 |

首次启动：

```bash
cp .env.example .env
docker compose up -d --build
```

部署前必须修改 JWT、数据库、MinIO 和模型密钥。生产环境不应直接使用示例默认密码，也不应把 `.env` 提交到版本库。

ARQ 默认使用 `REDIS_URL` 的 DB 0；Skills 和知识库列表缓存使用 `REDIS_CACHE_URL` 的 DB 1。
`SKILL_CACHE_TTL_SECONDS` 与 `KNOWLEDGE_CACHE_TTL_SECONDS` 分别控制技能和知识库分页缓存时长。
`REDIS_CACHE_TIMEOUT_SECONDS` 控制缓存读写超时；缓存不可用时短暂熔断并直接回源 PostgreSQL
或进程内 Skill 快照，不影响核心业务。

## 2. 数据卷与网络

- `pg_data`：PostgreSQL。
- `redis_data`：Redis AOF。
- `minio_data`：知识原件。
- `tool_workspaces`：Agent 会话工作区。
- `user_memories`：用户长期记忆。

`tool-runner` 同时位于内部网络，使用只读根文件系统、tmpfs、capabilities 清空、`no-new-privileges`、PID/CPU/内存限制。`TOOL_RUNNER_TOKEN` 用于后端到 Runner 的服务认证，生产环境应设置为随机值。

## 3. 模型适配

`backend/app/services/model_provider.py` 统一创建 LangChain Runnable 模型，业务层不直接依赖某一供应商 SDK。当前支持：

- Ollama 本地 Chat 和 Embedding。
- OpenAI 兼容接口。
- Azure OpenAI 兼容网关。

对话请求可以选择模型；查询改写、rerank、标题和评测裁判可使用独立配置，留空时按 ModelProvider 的回退规则选择默认模型。

会话自动压缩按所选模型上下文窗口的 80% 触发。Ollama 模型自动读取运行实例 `/api/ps` 返回的实际 `context_length`，多实例取最小值；外部模型使用 `MODEL_CONTEXT_WINDOWS` JSON 映射，例如 `{"model-name": 131072}`。未配置且无法查询时回退到 `MODEL_CONTEXT_WINDOW_FALLBACK`，默认 32768。

多模态对话使用 LangChain 标准 `HumanMessage` 内容块传递文本和 `image_url`。聊天图片先经过大小、MIME 与文件签名校验，再按 JWT 用户隔离保存到 MinIO；模型调用时才读取并转成 data URL。`CHAT_IMAGE_MAX_SIZE_MB` 和 `CHAT_IMAGE_MAX_COUNT` 分别控制单张大小与单轮数量。所选 Ollama 或 OpenAI 兼容模型必须支持视觉输入，否则模型服务会返回能力不匹配错误。

Embedding 模型与 `RAG_EMBEDDING_DIM` 必须一致。更换维度后需要新 collection 或重建已有向量，不能直接复用不兼容数据。

## 4. Ollama 多实例

`OLLAMA_BASE_URLS` 可配置多个逗号分隔地址；未设置时使用 `OLLAMA_BASE_URL`。`ollama_load_balancer.py` 负责：

- 优先选择进程内进行中请求最少的端点，平局时按游标轮询。
- 让聊天、embedding 和结构化调用通过同一端点选择入口。
- 在明确启用 `OLLAMA_RETRY_OTHER_ENDPOINT_ON_FAILURE` 时尝试其他实例。

负载均衡是应用进程内轮询，不是跨进程全局调度。多 Uvicorn Worker 或多个后端副本各自维护计数器，整体只能视为近似均衡。

失败重试必须限制在安全边界：

- 连接失败、连接超时等“请求大概率未执行”场景可切换端点。
- 已开始返回内容、普通业务 4xx 或参数错误不应盲目重试；当前实现把 Ollama 404 视为可切换端点的故障，以兼容某个实例缺少模型的情况。
- 流式输出开始后不能无提示切换模型重放，否则可能重复内容。

各 Ollama 实例需要预先拉取相同模型。应用不会自动同步模型文件。

## 5. 超时

不同链路使用独立超时：

- 对话模型单次请求：`MODEL_REQUEST_TIMEOUT_SECONDS`。
- Embedding：`OLLAMA_EMBEDDING_TIMEOUT`。
- RAG rerank：`RAG_RERANK_TIMEOUT_SECONDS`。
- 工具（含 Shell）：`TOOL_TIMEOUT_SECONDS`。
- Agent 总运行：`AGENT_TIMEOUT_SECONDS`。
- 标题和评测裁判：各自配置。

外部调用必须同时考虑连接和读取阶段。增强功能超时应按业务约定降级，身份、权限和数据一致性错误不能静默降级。

## 6. 常用检查

```bash
docker compose config
docker compose ps
docker compose logs -f backend
docker compose logs -f kb-worker
docker compose logs -f tool-runner
```

部署问题优先检查：

1. 容器内地址是否使用服务名而非 `localhost`。
2. PostgreSQL、Redis 和 MinIO 健康状态。
3. Alembic 是否升级到当前版本。
4. Worker 与 backend 是否加载同一模型和知识库配置。
5. Ollama 模型是否存在、embedding 维度是否匹配。
6. 数据卷权限和磁盘空间。
7. 日志中是否意外打印密钥或完整敏感文档。
